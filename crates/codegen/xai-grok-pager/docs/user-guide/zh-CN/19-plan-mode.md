# 计划模式

计划模式是结构化的规划阶段：agent 先探索代码库并设计实现方案，再写任何代码。适合实现路径本身就不清楚的任务——先征求你的意见，能避免大量返工。

---

## 计划模式做什么

计划模式开启后，agent 会：

1. 阅读并搜索代码库，理解现有模式和架构
2. 设计实现方案并写入计划文件
3. 可能用 `ask_user_question` 澄清具体问题
4. 调用 `exit_plan_mode` 把计划交给你批准

计划模式除计划文件外只读：对计划文件的编辑（会话目录里的 `plan.md`）会自动批准，对任何其他文件的编辑会被直接拒绝——工具调用失败，并给出一条短消息，说明只有计划文件可写。这在每一种权限模式（包括始终批准）下都成立。把规划和实现分开，让你在写代码前就能审阅并纠正方案。

---

## 如何进入计划模式

### Agent 主动进入

当 agent 判断任务存在真正的歧义时，会进入计划模式。它调用 `enter_plan_mode` 工具，需要你批准后计划模式才生效。若你拒绝，agent 留在普通模式。

**适合进入计划模式的触发：**

- 「给应用加上用户认证」——路径本身就有歧义（session vs JWT、令牌存储、中间件结构）
- 「重新设计数据管道」——大重构，选错方案会浪费大量精力
- 「给 API 加缓存」——多种合理方案（Redis vs 内存 vs 文件）
- 「加实时更新」——架构选择（WebSockets vs SSE vs 轮询）

**不适合计划模式：**

- 「在用户资料页加一个删除按钮」——实现路径清楚
- 「修 README 里的错别字」——直截了当
- 「更新 API 的错误处理」——先动手，需要时再问具体问题
- 「我们能做搜索功能吗？」——用户想开工，不是想规划

### 用户主动进入

你可以自己用两种方式进入计划模式：

- **`/plan`** —— 进入计划模式。你发送下一条提示时计划模式才激活。运行 `/plan <description>` 可一步进入计划模式并带着该描述开一个回合。
- **Shift+Tab** —— 循环会话模式：普通 → 计划 → 始终批准 → 回到普通。从普通模式按一次就到计划。

计划存在之后，运行 **`/view-plan`**（别名 `/show-plan`、`/plan-view`）可重新打开已保存的预览。

## 计划文件

计划写在会话目录里的 `plan.md`（`~/.grok/sessions/<cwd>/<session-id>/plan.md`，其中 `<cwd>` 是编码后的目录名，不是字面路径）。

计划文件包含：

- **Context** 段，说明为什么要做这次改动
- 推荐方案（不是每一种备选）
- 需要修改的关键文件路径
- 可复用的现有函数和工具，以及它们的路径
- 验证段，描述如何端到端测试这些改动

---

## 计划批准

agent 规划完成后会调用 `exit_plan_mode`。工具从磁盘读取计划文件，TUI 打开可滚动的计划预览，底部有操作栏。

若 agent 退出时没有写出计划（`plan.md` 为空或缺失），同一批准界面仍会打开，并给出明确的空状态，让你可以批准并开始实现、要求修改（把 agent 送回规划），或退出。在极简模式下，空提示会写入回看区，控件条标题为 **No plan written yet**。

### 审阅计划

用方向键或 `j`/`k` 滚动计划。操作栏显示这些快捷键：

| 快捷键 | 动作                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------- |
| `a`      | 批准计划并开始实现。若有未发送评论，这里会显示 `approve w/ comments`，批准时一并发送。 |
| `s`      | 要求修改。焦点移到提示框，输入修订说明后按 `Enter` 发送。 |
| `c`      | 对选中行或行范围评论。                                                          |
| `y`      | 把完整计划复制到剪贴板。                                                                 |
| `q`      | 放弃计划 —— 不批准并关闭计划模式。                              |

按 `Tab` 在计划预览和提示框之间切换焦点。

批准视图打开时，`Ctrl+P`（命令面板 → 模型）仍可在按 `a` 批准前切换模型。

### 提供反馈

批准视图有三种焦点状态：

- **预览**：滚动计划并选中行来评论。
- **评论中**：给选中行范围加行内评论（按 `c`，或在一行上按 `Enter`）。
- **提示框**：输入自由修订说明。

按 `Tab` 在预览和提示框之间切换。你发送反馈（行内评论、自由说明，或两者）后，agent 会收到并修订计划。计划模式保持开启，方便迭代。

### 离开批准视图

按 `Esc` 把焦点从提示框回到计划预览。若既不批准也不发送反馈，按 `q` 放弃计划。放弃会丢掉提议的计划并关闭计划模式。

## 计划模式生命周期

计划模式状态机有四个状态：

| 状态          | 说明                                                    |
| -------------- | -------------------------------------------------------------- |
| `Inactive`     | 普通运行模式。没有计划模式约束。               |
| `Pending`      | 客户端已打开计划模式，但还没发送提示。  |
| `Active`       | 计划模式已激活。计划文件编辑自动批准；其他文件编辑被拒绝。 |
| `ExitPending`  | 回合进行中时用户关闭了计划模式。          |

转换：

```
Inactive    --> Active   (enter_plan_mode 工具被调用并批准 —— 跳过 Pending)
Inactive    --> Pending  (你用 /plan 或 Shift+Tab 打开计划模式)
Pending     --> Active   (你的第一条提示激活计划模式)
Active      --> Inactive (exit_plan_mode 获批，或空闲时关闭计划模式)
Active      --> ExitPending (回合进行中关闭计划模式)
ExitPending --> Inactive (该回合结束后)
```

计划模式状态会持久化到磁盘，进程重启后仍在。瞬时状态（`Pending`、`ExitPending`）重启时会收成 `Inactive`，因为它们依赖进行中的交互。

## 计划模式中的编辑

计划模式激活时，对计划文件的编辑会自动批准、不弹窗，agent 可以自由迭代计划。对**任何其他文件的编辑在执行前就被拒绝**——agent 会收到一条短消息，说明只有计划文件可写。

这套约束独立于权限模式：

- **始终批准（yolo）在计划模式底下仍然武装。** 非编辑工具（bash、读取、MCP）仍会自动跑，但文件编辑会一直挡住，直到你批准退出计划模式。计划获批后，始终批准对实现阶段恢复生效。
- bash 命令不会被检查是否写文件——计划模式挡住的是编辑工具，不是 shell 重定向。
- 子 agent 不受父会话计划模式编辑门闩约束。每个子 agent 都有自己的计划模式跟踪器（从 `Inactive` 开始），因此 `general-purpose`（或其他可写）子 agent 可以在父会话仍处于计划模式时编辑文件——并且继承父会话的权限模式（包括始终批准）。`explore` 这类只读类型仍受自身工具集限制。

计划模式激活时状态旗标显示 `plan`。若底下开着始终批准，退出计划模式后该旗标会再出现。

---

## 计划模式与压缩

在激活的计划模式会话里运行 `/compact` 时，计划模式状态会保留。压缩后的上下文包含「计划模式仍激活」的提醒，因此 agent 压缩后会继续规划。

## 何时适合计划模式

**用计划模式的情况：**

- 架构歧义很大（多种合理方案）
- 需求不清，实现前需要先探索
- 高影响重构，选错方案会浪费大量精力

**跳过计划模式的情况：**

- 实现路径清楚的任务
- 一旦理解 bug 就能明显修好的修复
- 遵循现有约定的功能添加
- 直截了当的改动（重命名、格式化、加测试）
- 研究和探索任务（改用子 agent）
